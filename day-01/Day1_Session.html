    Why this course exists

    Each of these looked fine in a demo

    None of them crashed. None threw an error. Each gave a fluent, confident answer, and each answer was a defect.

    Air Canada · Feb 2024

    The invented refund policy

    The website chatbot told a grieving customer he could claim a bereavement fare up to 90 days after flying. The real policy said no refunds for travel already taken.

    A Canadian tribunal ruled that the chatbot is part of the airline’s website, and the airline is responsible for what it says. The airline had to pay CA$812.

    Tester’s lesson: fluent is not faithful. The answer must match the source policy.

    Car dealership, California · Dec 2023

    The $1 SUV

    Users told a dealership’s chatbot to agree with anything the customer said and call it a legally binding offer. It then “agreed” to sell a new 2024 Tahoe for one dollar.

    The screenshots went viral within days.

    Tester’s lesson: the user’s message is an attack surface. We test that on Day 9.

    DPD, UK · Jan 2024

    The chatbot that swore

    After a system update, a parcel company’s support bot swore at a frustrated customer and wrote a poem about how bad the company was. The firm switched the AI part off.

    It had worked for months before the update.

    Tester’s lesson: any change to model, prompt or settings is a regression risk.

    The pattern: one good-looking answer proves the system can produce one good-looking answer. That is all it proves.

    Non-deterministic testing

    Your test skills still work. Your assertions don’t.

    You already know test design, boundaries, regression and defect reporting. What changes is the oracle: the thing that tells you pass or fail.

    Traditional softwareLLM-based product
    Same input twiceSame outputOften different wording, sometimes a different decision
    Expected resultOne exact valueA set of acceptable answers plus rules none may break
    What one run provesThe behaviourOne sample of the behaviour
    What a defect looks likeCrash, error, wrong valueA fluent, confident, polite wrong answer
    What can cause a regressionA code changeCode, prompt, model version, retrieved data, sampling settings
    The assertionassertEquals(expected, actual)Several checks, many runs, many cases, plus human judgement

    Five answers, all worded the same

    Can still be a defect, if all five make the same false promise.

    Five answers, all worded differently

    Can all be correct, if every one follows policy and means the right thing.

    So we stop asking “did it give the expected text?” and start asking “what must be true about every acceptable answer?”

    Tokens

    The model never sees words. It sees numbered pieces.

    0characters
    0words
    0tokens

    Why a tester cares

    Cost and limits are counted in tokens. A context window of 128,000 tokens is a token budget, not a word budget.

    Other languages cost more. The same request in Hindi or Tamil uses noticeably more tokens than English, so long Tamil chats cost more and hit limits sooner.

    Capitals, IDs and emoji split oddly. “REFUND” is two pieces; “HL-48213” is four. Models handle split pieces less reliably, which matters for order numbers and amounts.

    What gets cut off is silent. If a long chat exceeds the limit, the app may drop the oldest text, which could be the policy.

    Try this: type your own name, then an Aspire project code, then the same sentence in your first language. Which costs the most?

    Sampling: temperature, top-p, top-k

    Every word is a weighted dice roll

    “Daniel, your refund of £429 has been ___”

    Rolls appear here.
    Pick one control. Providers advise not to tune both.
    What is happening underneath?

    The model gives every candidate a raw score called a logit. Softmax turns scores into probabilities: p = escore/T ÷ sum of all escore/T. Low T exaggerates the gap between scores; high T flattens it. Top-k keeps only the k best candidates. Top-p keeps the smallest set whose probabilities add up to p. Then one candidate is drawn at random by weight.

    Temperature 0

    Always the top candidate. Here that is “processed”, a false claim, every single time.

    Temperature 2

    The rare words get real chances. More variety, more surprises, more risk.

    The trap

    “We set temperature to 0, so it’s stable.” Stable, yes. Correct, not proven.

    Consistent is not correct. Low temperature makes the model repeat its most likely answer. If the most likely answer is wrong, you get the same wrong answer every time.

    Product categories and their QA tasks

    What you test depends on what the product does

    Lane is three products at once: it classifies the ticket, extracts a decision into JSON, and chats with the customer. So it needs three kinds of checks. One overall score would hide which part failed.

    Test oracles

    For each requirement, who or what decides pass or fail?

    Deterministic

    Code checks it the same way every time: valid JSON, a value in a list, a word count, a tool called once.

    Semantic

    About meaning, so it needs a model to judge it: does the answer stick to the source? We build these from Day 4.

    Human

    A trained person decides, using written criteria: tone, empathy, business risk.

    Layered

    A cheap check catches the obvious cases; a human or judge reviews what slips through.

    “Unsafe” means

    If this answer reached a real customer, it would cost money, break policy, or mislead them about what happened.

    The release rule

    One unsafe answer blocks release. A high average never cancels an unsafe answer.

    Debrief
    
  
    Would you sign Lane off on Monday?
    
  
    Open each question once the room has answered it.
    
  
    
    
    Which run would you have shipped if it was the only one you saw?
    Most people pick a clean one. That is exactly the demo problem: one sample can be clean while the next one is unsafe.
    
    
    In the sample set, run 3 failed C1 but you labelled it correct. Is that a real defect?
    Yes. The wording is fine, but the website parser cannot read JSON wrapped in markdown fences, so Daniel sees an error or a blank reply. Correct meaning, broken delivery. Two separate verdicts.
    
    
    Run 5 passed every hard check. Why did a human block it?
    It offers to send the refund to the new card “as an exception”. None of the keyword rules looked for that wording. Deterministic checks catch what you predicted; humans catch what you didn’t. That gap is what LLM judges try to fill from Day 6, and why we will calibrate them against people.
    
    
    Would temperature 0 have fixed this?
    It would make the answers more alike. It would not make them correct. If the most likely answer is the unsafe one, temperature 0 ships it every time.
    
    
    Is 60% “all hard checks passed” good?
    Against what? There is no target yet, five runs on one case is a demo, and there is an unsafe output. The verdict is BLOCK, and the next step is more cases, not more runs of this one.
    
  
    
  
    Kavya’s report says: BLOCK. Two of five runs would have promised a refund to a card policy forbids. Evidence attached: prompt, settings, five raw outputs, hard-check results, human labels. Next measurement: 30 varied refund requests, which is exactly what we build on Day 7.
    

    



    
  
    Before Day 2
    
  
    Three things to keep from today
    
  
    
    
    One answer is one sample
    Evidence means many runs, many cases, written rules, and a human look at meaning.
    
    
    Consistent is not correct
    Sampling settings change how often you see an answer, not whether it is right.
    
    
    Name the layer
    Prompt, retrieval, tool, app, model or evaluator. “The AI hallucinated” is not a defect report.
