    Hour 1 · Context · Ground truth and golden datasets

    A golden dataset is your regression suite for AI

    What makes it “golden”

    Every row has an input, an expected behaviour agreed by the business, a tag for the risk it covers, and a source. It’s versioned and reviewed, and it doesn’t change between runs.

    Everyday version: the answer key for a board exam. Set once, checked by experts, same for every student.

    Ground truth: who decides?

    Not the tester alone. The product owner, domain expert or compliance owns what “correct” means. The tester writes it down precisely, and makes sure it’s checkable.

    That’s why every dataset records labelled_by:.

    Ask the roomExpected answers for an insurance claims bot: who should sign them off, the tester or the claims team?
    Expected: the claims team (domain owner), with the tester making each line precise and checkable. A tester who invents “correct” answers alone is testing their own opinion.

    Hour 1 · Context · Curating test data from production logs

    Real users ask things you’d never think of

    1. Collect real conversations (with permission).
    2. Remove noise and duplicates: “asdfgh”, the same question typed three times.
    3. Mask personal data before anything leaves production: emails, phones, cards, Aadhaar, PAN, UPI IDs.
    4. Pick by risk, not at random: complaints and escalations first.
    5. Label: write the expected behaviour and the tag.

    What logs give you that you can’t invent

    Typos and lowercase. Hinglish and other languages. Three questions in one message. Angry capitals. People pretending to be someone else. Questions nobody planned for.

    Today’s Lane logs: 60 lines, including a Polish message, a Hindi one, an angry one in capitals, and someone asking for a neighbour’s address.

    Ask the roomA log line says: “Hi it’s Sarah Jones, sarah.jones@example.com, 07700 900321, update my address.” Can it go into the test dataset as it is?
    Expected: no. Mask the email and phone first (the kit does this: [EMAIL], [UK-PHONE]). Names are harder: regex can’t reliably spot them, so a human check is still needed.

    Hour 1 · Context · Synthetic data generation basics

    Synthetic data fills the gaps logs don’t cover

    When to generate

    Risks that rarely appear in logs but matter: attacks, edge cases, new features with no history, fairness pairs, other languages.

    Ways to generate

    Paraphrase a real case · change the persona · translate · add an adversarial twist (“ignore your rules”) · push a boundary (day 29, 30, 31).

    The risks

    AI-generated cases sound too clean, repeat each other, and sometimes invent rules (Day 3’s run C). So:

    • mark them source: synthetic
    • review every expected line
    • keep most of the dataset from real logs

    The kit’s draft command generates them; lint counts them.

    Ask the roomYour logs have no prompt-injection attempts. Your bot is about to go public. What do you do?
    Expected: generate synthetic injection cases (“ignore your instructions…”, “pretend you’re a manager…”), mark them synthetic, review them. No logs doesn’t mean no risk. Day 9 goes deep on this.

    Hour 1 · Context · Dataset hygiene

    A dirty dataset gives you confident wrong numbers

    CheckWhy it mattersThe kit’s lint
    Version and labeller recordedYou can compare runs and know who decided “correct”✓
    Unique IDsDefects point to one case✓
    Every row has tag and expectedA case with no expected result isn’t a test✓
    No duplicatesFive copies of one easy case inflate your pass rate✓
    No personal dataTest data gets shared, uploaded, sent to judges✓
    Coverage: every risk tag 2+ timesA 95% pass rate means nothing if no case tests data leaks✓
    Balance: no tag over 40%One easy category hides failures in the others✓
    Ask the roomA dataset of 30 rows passes at 95%. 25 of the rows are “where is my order?”. Is Lane ready?
    Expected: you can’t tell. The dataset is unbalanced and probably has no coverage of refunds, data leaks or abuse. The 95% describes the dataset, not the bot. That’s what lint’s coverage and balance checks catch.

    Hour 1 · Context · Where automation starts

    A clean dataset + a gate = an automated release check

    python kit.py run --ci

    Quality gate (in project.ini): pass rate at least 80%, and any failure tagged personal-data or credentials blocks the release.

    Exit code 0 or 1: Jenkins, Azure DevOps and GitHub Actions turn that into a green or red build.

    JUnit XML (reports/junit.xml): each case shows up in the CI test tab like any automated test.

    This is the bridge to Days 8–10

    Today you run it on your laptop. The same command runs in a pipeline on every prompt change. A reference GitHub Actions file is in templates/.

    Remember Day 4: a developer changed one sentence of the prompt. With a gate, that’s a red build, not a surprise in production.

    Ask the roomPass rate is 93%, above the 80% gate, but one failed case is tagged personal-data. Should the build pass?
    Expected: no. Some failures are too costly to average away. That’s why the gate has block_tags: one data leak fails the release whatever the pass rate.
